# Window checks

[한국어](window-checks.ko.md)

The window checks of the term view run in this repository, against the published core application of one core release, through `@soksak/window-check` ([window checks of a plugin](https://github.com/soksak-app/core/blob/main/docs/spec/plugins.md#window-checks-of-a-plugin)). They read no source of core and name no path of its repository.

## Run

```sh
make install     # once: installs the locked dependencies, among them @soksak/window-check
make test-app    # pnpm exec sok-test-app
```

`make test-app` runs on a computer with a display, only locally. No workflow of this repository runs it, because the checks need a running application that presents frames; `make test` and `make check` are the checks of CI.

`package.json` names the release file of the package as a development dependency, `https://github.com/soksak-app/core/releases/download/v<version>/soksak-window-check-<version>.tgz`, and the version is a core release inside `engines.soksak`. The version of the installed package selects the application of the run: `sok-test-app` downloads the application zip of that core release into `build/app-cache/<version>/`, packs this repository with `make pack OUT={out}`, installs the plugin and its sidecar into a new configuration folder under `build/test-app/`, starts the application with that folder, runs `node --test` on the files under `e2e/`, and quits the application. A passed run removes its folder; a failed run keeps it. The package holds `@soksak/client`, `@soksak/log-contract` and `@soksak/plugin-api` inside its release file, so pnpm installs it with its default settings; `pnpm-workspace.yaml` allows the build script of `@parcel/watcher`, which the package uses to watch folders.

The same checks run against development builds of core and against development checkouts of this plugin and of its sidecar: each application of the run starts from its build with `--config-dir <root>/soksak-check-<app>`, whose `plugins/installed.json` lists the plugin, the start probe of `@soksak/window-check` and the sidecar, and whose plugin and sidecar folders are symbolic links to the checkouts; `node --test e2e/` then runs with `SOKSAK_CONFIG_ROOT=<root>` and `SOKSAK_BINARY_WAILSV3`, `SOKSAK_BINARY_TAURIV2` and `SOKSAK_BINARY_MYGO` set to the executables of the builds. The checks start no application in either run.

`test/window-checks.test.mjs` checks the declaration: the development dependency names a core release file of the package inside the `engines.soksak` range, `e2e/` holds the check, and `make test-app` runs `pnpm exec sok-test-app`.

## Checks

`e2e/term-view.test.mjs` runs two tests for each application of the run. Each test has its own time limit of 180 seconds, waits on statuses and records (no timer), uses only the input that the host emulates inside the application, and starts from the state that `fresh` of `@soksak/window-check/start.mjs` prepares in a disposable configuration folder, with the shell `e2e/check-shell` (its prompt is `sh-3.2$`).

- The process contract: `runViewMeasurements` judges the measurements of `collectViewStartAndMemory` and `collectViewReclaimMeasurements` against core `docs/spec/plugin-processes.md#pass-values`: the memory of one view and of three views, the five process starts, the first display and the warm reuse (the plugin has no recorded DOM mount baseline, so the first display is judged against the margin alone), and the reclaim of the process group when the views close. A view counts as displayed when `term.screen.read` shows the prompt in the visible document region.
- The frame contract: after a card width change the image region `view` presents a raster of its new frame size (`host.window` regions `presented`), the screen read shows the prompt at that size, and the view reports at least one content frame with the dimensions of its document while its observer (`term.view.frames`) runs.

`e2e/messages.test.mjs` runs one test for each application of the run, with a time limit of 180 seconds, from the state that `fresh` prepares with the shell `e2e/check-shell`: an agent of one terminal waits for and reads the message of another terminal (core `docs/spec/messaging.md#path-of-the-reads`). The check opens a project window with `core.project.open`, because a terminal registers its folder `<root>/.soksak/messages/<surface>` only in the window of a project, and opens a reader tab and a sender tab beside it. The agent is a script: the MCP client of `@modelcontextprotocol/sdk` runs `sok mcp` of the application with `SOKSAK_SURFACE` of the reader, so no agent program, account or prompt takes part. It reads the empty folder with `messages_read`, calls `messages_wait` with the returned cursor, waits for the open call in `core.plugin.open-calls`, and types `sleep 11 && sok message send` into the shell of the sender with `term.input`, so the wait lasts beyond the 10 seconds after which the sidecar records a request in progress as an error and each error of the application log fails the check; the send prints `{path, receiver}` with the receiver `{surface, plugin: "term", held: null}` of the reader; the wait answers the one message of the sender with the written file, the text and the sender, the page of the reader injects the message and reports it in `last` of `term.messages` as `injected` (core `docs/spec/messaging.md#injected-message`), and a second `messages_read` with the same cursor answers the same message.

`e2e/injection.test.mjs` runs three tests for each application of the run, each with a time limit of 180 seconds, in a project window with a receiver tab and a sender tab and the shell `e2e/check-shell`; it writes each message with `sok message send` of the application for the surface of the sender and judges the reply, `term.messages` of the receiver and its screen (core `docs/spec/messaging.md#injected-message`). The shell reports no OSC 133 mark, so the submitted line is judged by the error line of the shell: `[메시지: not found` for a report and the syntax error of the parenthesis of the report request for a message.

- A running command: the receiver runs `cat <named pipe> > /dev/null; echo command-ended`; the reply shows `held: null`, `term.messages` reports the message as `injected` while the command runs, and after the check writes the pipe the shell submits the injected line after the line `command-ended`.
- A blocked program: the receiver runs `e2e/blocked-prompt`, which reports `state=blocked:kind=permission` with OSC 7501, shows `Proceed? [y/N]` and reads one line; the reply shows the hold `blocked` of kind `permission`, `term.messages` holds one message with no decision, and the screen shows no byte of it; after the answer `y` through `term.input` the program prints `answer=y`, and the page then injects the message, which the shell submits after that line.
- A report: the sender writes a message, which holds the request `(끝나면 결과를 sok message send --reply <sender folder> "<보고>"로 보고하라)` with the folder of the sender (core `docs/spec/messaging.md#report-request`) and is injected into the receiver; the check then writes `sok message send --reply <sender folder> done` for the surface of the receiver, whose file `<receiver>.report-<token>.txt` holds `done` alone, and `term.messages` of the sender reports it as `injected`.
